## Step1 问题与反问
【问题 1】复习日志 `korean_wordlist_review_log` 只存本地——换设备后连续复习天数/近 7 天柱状图全部归零。
- 反问 1（真实性）→ 真实：AGENTS「已知坑点」明言其不同步；导出/导入是手动搬运。
- 反问 2（架构假设修正）→ 坑点原文「服务端没有对应 blob 列会静默丢弃」已**过时**：D1 的 `user_blobs` 是通用 (user_id, key) 键值表，真正的闸门是 `functions/api/_shared.js` 的 `BLOB_KEYS` 白名单（一行）与前端 `SYNC_BLOB_MAP`。**无需建表/迁移**——AGENTS 与设计文档的机制描述需随本轮更新（已改 app.js 注释，AGENTS 修订随收尾轮）。
- 反问 3（合并语义——本轮核心反问）→ 不能复用 arr 型：`mergeArr` 按 id 后写胜出，而复习日志**同一词条 id 可多日重复出现**（复习 10 天 = 10 条同 id），arr 会把多日折叠成 1 条吞掉历史。→ 新增 `set` 型：按 `id+time` 并集、append-only、无墓碑（删除不在产品语义中，过期走既有 90 天本地修剪）。
- 分论点：a) 90 天窗口两端独立修剪后再并集——修剪过的老条目从云端回来属预期（并集设计，跨端历史以导出包为准）；b) 墓碑机制对 append-only 无意义且引入 clearedAt 复杂度；c) 2MB blob 上限对 90 天 × 日均几十条的日志量级绰绰有余。

4. 新增 `tests/e2e/review-log-sync.js`（独立 pages dev + 独立 D1 persist）：白名单命中 / set≠arr 三条目 / 后写胜出 / 幂等 / 修剪；
